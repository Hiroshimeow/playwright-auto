# Recovery trigger learning

- Preserve the exact accepted-send receipt, task/hop ownership, and conversation URL while releasing a blocked task; recovery must resume durable work rather than replay it.
- Treat immediate release, durable source repair, concrete defect recording, and reusable learning as separate decisions; `PROBLEM.md` holds incident evidence while trigger learning holds only generalized invariants, and report recovery must preserve canonical role-turn evidence, never overwrite different existing content, and consume a proven accepted response without replay.
- Claim only continuously blocked work after its eligibility window, process the oldest eligible target one at a time, and apply per-target plus inter-target cooldowns to prevent recovery thrash.
- Classify transport failure from bounded UI/error evidence rather than arbitrary phrases quoted inside role content, and distinguish pre-durable send preparation from a crossed accepted-send boundary before blocking or replaying recovery.
- Do not treat a role-report file existing or having an early mtime as proof that the assistant turn is complete; tool-using roles may write the report while response activity continues. Diagnose completion from the exact durable response/stable final assistant turn plus inactive transport, and treat recent response-activity changes as ongoing work. Once that stable accepted response is proven complete, route report and response-validation failures through the same bounded repair state machine as normal waiting rather than collapsing them into a generic recovery failure that changes incident eligibility while leaving the durable hop stranded.
