# LEARNING.md

Reusable lessons for CDPA teams. Read before starting a task. Add only evidence-backed lessons that are likely to prevent mistakes in future tasks; do not turn this into a chronological activity log.

## Durable transport

- Observational diagnostics must verify that every helper is actually read-only before using it in shadow or projection paths. A getter that takes an exclusive lock, rewrites durable state, or fsyncs on exit is a mutation path; diagnostics should consume copied or already-loaded facts instead, and return unknown when a side-effect-free observation is unavailable.

- Persist state before and after every send boundary. On restart or CDP reconnect, distinguish `pre_send`, `sending`, `sent`, `responded`, and `routed`; never infer that an ambiguous send is safe to repeat. A workflow hop label is progress metadata, not authority that Send crossed: any control or recovery decision that could discard, rebind, upload again, or resend must consult the exact durable request boundary and accepted provenance, because a hop may be labeled `sending` while the request is still pre-acceptance. Browser/transport disconnect exceptions must escape per-task blocking logic so the reconnect supervisor can attach again without changing hop, request, report, or control identity. Supplemental frontend network identity is shadow evidence around that same Send: DOM acceptance remains authoritative, body parsing must not gate acceptance or authorize replay, and asynchronous enrichment may update only the exact durable request whose accepted user identity matches. Before exact-page recovery classifies a conversation mismatch, reconcile provisional `WEB:*` identity from the immutable-matching durable ledger; canonicalization may enrich identity but must never authorize replay or rebind. When a pre-boundary role context is lost, never use conversation generation alone to authorize replacement: require durable acquisition/control provenance that proves the context was fresh and equivalent, and fail closed when attachments or accepted/ambiguous Send evidence make ownership non-transferable.
- Before an irreversible upload/send boundary, validate and use the same immutable byte snapshot. After the exact request crosses that boundary, recover from persisted durable evidence rather than rereading mutable source inputs. When bounded recovery authorizes repeating a pre-boundary browser mutation whose prior failure is proven, persist one exact one-shot authorization and durably consume it before invoking the browser mutation; a crash after consumption must return as ambiguous/fail-closed rather than silently replaying the mutation. Reusable bootstrap context follows the same boundary: normal task creation durably resolves the selected/default bootstrap, while explicit operator-selected None/Fresh remains the compatibility path. Before Send, lazily branch from ordered bounded donors, prefer descendant child-local fork points, retain donors across transient failures, remove only donors proven permanently unavailable, regenerate only from an explicit prewarm prompt when all donors are gone, and otherwise block as bootstrap unavailable rather than silently opening Fresh context. After Send is accepted or ambiguous, donor switching, branching, regeneration, and resend are forbidden; the canonical role conversation and durable request reconciliation solely own recovery.
- Once send acceptance is persisted, consume only an assistant message newer than the pre-send baseline. Persist the accepted user message/turn identity and match either non-empty identity after restart or F5 because DOM message IDs may change while turn IDs survive. When durable identity exists, never fall back to rendered text; long prompts may be collapsed behind `Show more`.
- Absence of the accepted user identity from the current rendered snapshot does not by itself prove that the exact conversation or page binding changed. A long role conversation may retain the same page ID and conversation URL after `page_missing`/`page_seen` while the DOM exposes only a bounded subset of its messages. Resume must distinguish `not currently rendered` from `proven absent`: use the durable receipt plus an exact transcript/history retrieval path when available, never resend the accepted prompt, and provide an explicit operator-confirmed abandon/replacement path when provenance cannot be recovered instead of looping indefinitely in `recovery_required`.
- Structurally incomplete output with exact provenance is resumable waiting, not proof of failure. Unproven or stale output remains blocked.
- Rendered ChatGPT DOM may expose route JSON without Markdown fences. Parse the terminal JSON object, validate duplicate keys and all fields, and fail closed.
- A malformed route should trigger a bounded guide-only repair in the same tab. Repair input is compact identity plus validation error, shared guide, and generic naming rule; it must not resend the original task, handoff, constructor, or worker-computed report path.
- Resume is identity continuation, not task creation. Separate new-team-base normalization from exact existing-team validation: never truncate, lowercase, sanitize, or strip an allocated exact identifier, because its numeric suffix is durable identity. Inspect every raw catalog entry associated with that exact team by key, declared team, or path; malformed structures and duplicate path claims fail before selection. Compare every canonical catalog field—path, task, team, suffix, status, and update timestamp—exactly to the manifest before selection and again inside the manifest lock. Revalidate the selected candidate, then queue the shared durable resume control without changing task/hop/request/turn/report identity. Never reconcile away or silently rewrite corrupt catalog metadata.

## Browser and tab ownership

- When a late UI observation can refine the cause of a browser failure, apply it only to raw or untyped failures. Do not let ambient evidence such as a visible rate-limit modal overwrite a typed ownership, binding, composer, authentication, unsafe-page, or semantic bootstrap exception; stronger typed safety evidence keeps precedence and fails closed.

- For CDPA-owned ChatGPT pages whose wait path depends on renderer timers, reassert Chrome web lifecycle `active` through CDP at the existing ownership/wait boundary; never use foreground focus as a liveness mechanism, and fail soft if the experimental command is unavailable.

- Use the unique physical-role + team + task tuple as durable operating ownership. Treat `page_id` as replaceable runtime metadata during pre-send reconciliation, but never transfer an accepted in-flight receipt to another page. Fail closed when more than one exact owner exists.
- A deployment-wide coordination path must be CWD-independent before it protects ownership. Validate every path source—including explicit configuration and environment fallbacks—as absolute before resolution or directory creation; resolving a relative value against each repository CWD can split the ownership plane and permit duplicate sends.
- Tabs with no role are user-owned free tabs. Never allocate or clean them.
- Preserve the persistent Chromium process and profile. Attach/detach through CDP; never call `browser.close()`. For Snap-confined browser tests, place disposable Playwright profiles in a repository-owned temporary directory visible to both host and sandbox namespaces; otherwise native cleanup can remove only the host-side path while sandbox-private data accumulates.
- Stop is an urgent action and must not receive artificial human delay. Visible non-urgent actions may use the shared delay policy.
- Controlled reopen or restart must fail closed when the composer contains manual text or attachments; recovery must never discard user input to reclaim a role tab. Only a page provably created by the current bootstrap acquisition may receive one bounded pre-bind composer sanitation, and every supported native/UI fresh-page acquisition path must share that same fail-closed sanitizer so stale rehydration cannot escape through a fallback path.
- A Python-side snapshot and mutation lock are not atomic against user or DOM events between browser round trips. When live page safety gates a durable identity write, repeat the minimum predicates and the storage mutation in one synchronous browser callback; a failed predicate must leave the prior identity untouched.
- During a profile-wide rate-limit cooldown, freeze new browser mutations without destroying existing ownership: preserve owned ChatGPT tabs and durable request identity, allow accepted WAITING/SENT work to continue read-only backend/status reconciliation, and keep ambiguous SENDING fail-closed without resend or reacquisition. After the configurable quiet period, permit exactly one shared acquisition/probe; keep that permit in-progress for the full awaited mutation, and if throttling recurs reset the quiet period before any further probe.

## Response waiting

- In an exact CDPA-owned role tab, later operator user turns are valid continuation input and must not detach or deadlock the active hop. Read the current transcript, ignore assistant output before the latest user turn, keep waiting while the latest response is streaming, accept the latest stable assistant response, and use the existing bounded route-repair prompt when its route format is invalid. If the exact tab is offline, reopen its saved conversation URL and resume the same check without resending the task.
- Send-button visibility is not sufficient to prove response completion because the user may type while a response is active. When an active-response composer steer is accepted, treat it as part of the existing execution budget unless backend evidence proves a new request/exchange; an in-flight user message alone must not be assumed to reset the request/exchange cutoff.
- Response-state conditions belong in editable policy, not embedded flow branches. With durable conversation and accepted-user identity, use `stream_status` for normal waiting and one durably guarded full-graph read only after terminal status; bind that graph to the exact accepted user/current branch, and degrade backend failures to the existing DOM path without replaying Send. When terminal backend status is authoritative but the terminal assistant continuation is not yet materialized, keep the accepted receipt authoritative, consume at most the existing bounded refresh, and continue bounded recovery until the overall deadline instead of replaying the request. Without durable backend identity, the DOM responding signal and stable-response/provenance checks remain authoritative.
- While no valid response has been accepted, refresh after 20 minutes without assistant/transport activity when the composer is empty and no manual input is pending; Stop may be visible or hidden by timeout/error UI. Total wait budget is 120 minutes. Refresh count, activity signature, and timestamps must persist across worker restart. Every DOM observation needed to reach refresh or deadline reconciliation, including sparse probes, full-snapshot fallback, ownership checks, and final reconciliation, must have a Python wall-clock bound derived from the existing workspace timeout so one wedged page cannot prevent other tasks from being revisited. Treat only known page-lifecycle failures as resumable observation failures; recovery may reload only the already bound physical page and must re-prove exact page, role, task, and team ownership afterward before consuming, routing, or mutating, without replaying an accepted Send.
- Persist assistant IDs, turn IDs, and content fingerprints before F5. Union that recovery baseline across refreshes/restarts and reject matching pre-refresh output. Automatic recovery is F5-only; never click Retry or Regenerate.
- A stuck Stop button after content completion is an observed DOM edge case; use stable content and provenance evidence rather than Stop disappearance alone.
- Finality is a validated route/report observed unchanged across at least two samples, not merely Stop disappearance or a transport banner. Changing assistant content, connection-interrupted text, timeout UI, or recent DOM activity remains active work; only a clean, inactive, stable malformed candidate may trigger route repair. Immediately before a timeout block, make one final bounded read using the same provenance, stability, route, and report validator so a completed output at the deadline is accepted exactly once.
- Base recovery refresh on 20 minutes without assistant/transport activity, not continuous Stop visibility. Persist the latest assistant signature, length, last-change timestamp, message/turn IDs, and content fingerprints before F5 so a timeout banner that hides Stop can recover without Retry, Regenerate, or resend.

## Reports and state

- When executable policy can resolve from repository-local overrides or packaged defaults, test every supported resolution mode at generation zero and assert every derived asset exists. Keep intentional overrides explicit; do not rely on an untested mirror convention. For embedded third-party SDKs that must obey app-owned configuration, explicitly disable default global or user config discovery and add a poisoned-home regression proving global settings, models, and credentials cannot affect or be modified by the runtime.

- Large role reports belong in independent Markdown files. Cross-role handoffs reference the exact source report path, while the worker keeps the exact next output path internal and exposes only the generic naming rule. Invalid route JSON is repaired in the same role at most three times before blocking.
- Build agent prompts from one explicit physical-role allowlist: title, task ID, team, role, source role, turn, workspace, allowed logical routes, goal, and handoff. Do not serialize team rosters, manifests, or transport records; they leak redundant state and browser/controller metadata.
- Prompt contract tests must inspect the final composer/send payload and persisted receipt, not only `PromptBuilder` output; a shared durable layer can otherwise append forbidden transport markers after prompt construction.
- Machine state and human reports serve different purposes. Keep the atomic task manifest separate from role-authored Markdown reports.
- Only the worker/dashboard mutates task state. Concurrent agents must never edit the manifest directly.
- Treat report location as projected evidence, not durable identity: resolve legacy cross-repository files only from one strict declared repository with allowed-root and exact team containment, publish immutable hash/size before serving, and represent remote-host path-only reports as explicitly unmirrored rather than searching or rewriting history. Workflow turn numbers are role-local, not a global chronology; when selecting the latest report or event across different roles, use explicit timestamps first and a stable append/order signal only as fallback, never cross-role turn numbers as recency.

## Dashboard and operations

- Public mutation gates must reject attacker-controlled origin metadata before body parsing, authentication, or upstream side effects; when `Origin` is present it is authoritative, `Referer` is fallback only when `Origin` is absent, and malformed URL evidence must fail closed rather than escape the handler.

- Dependency readiness is an execution invariant, not a lane label. Reconcile every nonterminal workflow task before browser transport and after Resume or reload; unfinished, missing, or stopped parents force WAITING without changing the active hop or accepted-send evidence. Running independently requires an explicit exact-parent removal command with optimistic versioning and immediate scheduler reconciliation.

- Worker-published action eligibility must share the same canonical helper as locked command admission. A projection may fail closed on stale or unknown runtime evidence, but it must not add independent state prerequisites that hide commands the worker would safely accept.
- A worker-published execution-order projection must reuse the scheduler's dependency-ready frontier and FIFO key. Apply exact-team predecessor edges only across structurally valid waiters, keep intervention entries outside the queue graph, and republish every WAITING projection after dependency or ownership transitions so SQLite never exposes stale or contradictory order.
- Treat Resume as a worker-owned verified recovery attempt, not a status flip or ordinary recheck. Keep the command nonterminal until one bounded safe action proves a real postcondition such as response consumption, semantic generation progress, exact draft acceptance once, or hop advancement; otherwise persist `recovery_required` or `failed` with the concrete next safe action. Accepted user turns forbid resend. Manual composer or attachment conflicts gate only UI mutation/new Send; they remain untouched and must not gate read-only backend/response observation. Stale workers require explicit external restart plus a healthy heartbeat before retry. Worker liveness heartbeat publication must be driven independently of workflow-cycle completion on the worker's own asyncio event loop, reusing the bounded worker snapshot; healthy long awaits must not be hidden by increasing stale thresholds, and a blocked or dead event loop must naturally stop the heartbeat. A durable semantic reset must require the final successful control result, never an intermediate `recovering` state; after restart, unfinished control state must preserve the pre-control safety streak or workflow frontier until the verified postcondition is durably applied.
- Incremental updates must preserve text selection and scroll context; do not reload the full page during polling.
- Dashboard controls must request durable state transitions, and mailbox completion must represent the matching durable control terminal outcome rather than mere request delivery: a `requested` control keeps its command nonterminal until it becomes applied, rejected, ineffective, failed, or another explicit terminal outcome. Resume must report the rechecked result and Retry must require a structured retryable block. Clear Team preflight must fail on any supported-page inspection uncertainty, then persist `stop_pending`/`close_pending`/`closing`/`verify_pending`; once cleanup starts, nonterminal work is STOPPED with no active hop. Count only observed closures and require a clean post-close zero-match verification before `CLEARED`; otherwise preserve the phase and concrete error for restart. Control rollback/persistence paths must keep before/after snapshots structurally independent; a shallow restore that aliases nested control state can erase the terminal delta and leave the durable control plus mailbox command nonterminal forever.
- Apply the same strict primary-manifest validator to direct load, discovery, exact-team resume, catalog handling, and pre-replacement writes. For exact-team operations, raw catalog validation must not skip non-mapping or incomplete entries merely because a valid filesystem manifest also exists; key/path/team/task identity, required suffix/status/timestamp types, duplicate path claims, and full canonical catalog-to-manifest equality are checked before mutation and during locked revalidation. Malformed JSON in canonical `<team>/<task-id>/<file>.json` layout must remain a diagnostic and reserve its directory task ID/team suffix even when the catalog is absent; scope the reservation so unrelated team creation continues. Schema-shaped evidence, full copies under a second filename, partial manifests, `requests.json`, and poisoned catalog metadata are never executable tasks.
- Keep active work, fully offline recoverable work, and terminal History/Reports as separate projections of the same manifest. When CDP is disconnected, availability is unknown rather than offline. `CLEARED` is not sufficient to hide a task: while an exact assigned-role tab is observed, show a cleanup warning and permit Clear Team to re-verify and close it; History requires connected zero-match evidence.
- Discover only canonical primary task manifests. Arbitrary evidence JSON and request ledgers inside task directories must never enter worker or dashboard task loops.
- Normal client disconnects such as `BrokenPipeError` and `ConnectionResetError` are not operational failures and should not pollute logs.
- A non-DONE task is never automatically cleaned after one hour. DONE or STOPPED teams may be cleaned after one hour idle; active, paused, stalled, or blocked teams require explicit user action.
- Cache-busting modular frontends must follow the changed import graph, not only the HTML entrypoint: whenever published module bytes change, assign a new cache identity to that module and every changed nested static import needed by the deployment; never reuse a previously published query key for different bytes.

## Complexity control

- For schema-driven numeric inputs, coerce from the declared field contract (type, range, step, and control semantics) rather than from the runtime type of a default or current value. Acceptance must exercise at least one non-default valid value through the same shared service path, especially fractional values for sliders, because default-only smoke tests can hide deterministic truncation or coercion.

- For media-heavy UI acceptance, exercise real media against a representative dataset; fast listing APIs do not prove renderer usability. Inactive tabs and offscreen cards must not eagerly fetch or decode heavy media, and acceptance should verify both request fanout and browser responsiveness.

- Runtime acceptance evidence must identify the exact loaded source and every persistent helper process. A process started before material source changes is stale evidence for the current implementation; report browser automation drivers separately from both direct Python totals and the Chrome tree.
- Reuse `ChatGPTPage`, workspace ownership, durable ledger, and current response reader. Do not create a duplicate DOM reader or parallel orchestration stack. Retired coordinator code, scripts, docs, tests, and dashboard state bridges should be deleted rather than retained as compatibility surfaces when the canonical manifest worker fully replaces them.
- Separate components by responsibility, but avoid one-implementation interfaces and speculative plugin systems. A component boundary is justified when it can be tested and replaced independently.
- Parallel worktrees help only when modules are genuinely independent and start from a reproducible baseline. For source migrations from a dirty Git reference, take tracked files from immutable Git objects at the accepted commit; treat necessary uncommitted or no-HEAD material as explicit file-level evidence with hashes, never as a fabricated commit or bulk working-tree copy. If the live baseline includes dirty or untracked runtime files, a clean worktree is not equivalent to production: isolate from a byte-preserving snapshot or copy of the actual working tree. For production cutovers from copied or non-Git staging, freeze the independently accepted deployment files and hashes separately from a byte-preserving rollback snapshot before mutation; deploy only the explicit accepted manifest, preserve production-owned data and configuration except intentional bounded deltas, and verify both rollback material and loaded or served source identity. Do not split a large uncommitted diff merely to appear parallel.

- For character-exact OCR or document pipelines, verify serialized text exactness and rendered glyph coverage separately. Preserve source code points and display-significant number formatting without compatibility normalization, and include representative glyph checks because byte-deterministic rendering can still emit the same missing-glyph box for distinct characters.

## Engineering philosophy

- Prefer the simplest design that completely solves the real operational problem. Simplicity is valuable because it improves speed, clarity, reliability, and cost; it is not an excuse to remove safeguards or ignore known failure modes.
- Reuse proven core primitives before inventing architecture. If normal tasks, exact-team reuse, FIFO ownership, dependencies, worker commands, durable sends, and atomic state already express the required flow, extend them instead of adding another queue, coordinator, state store, protocol, or service.
- Represent one concept once. Capabilities that differ only by prompt and trigger should use one shared agent engine; do not create separate Maintainers, Monitor, Improver, or custom-agent orchestration stacks.
- Keep control flow direct: detect a trigger, activate the existing job, let the responsible agent investigate and act through normal tools, verify the postcondition, finish the job, then reuse or spawn the next waiting job.
- Use sequential work when it is sufficient. Oldest-first processing through existing job and exact-team ownership is preferable to parallel recovery machinery when only one agent may safely own the trigger.
- Express exclusivity with the smallest invariant that enforces it. An exclusive trigger has one enabled owner at a time; shared triggers remain reusable. Do not build a generalized lock or scheduling subsystem when one validated ownership field is enough.
- Let agents perform and verify operations directly when they already have safe tool access. Avoid model-to-worker action JSON, dispatch layers, and duplicated decision state unless a hard trust boundary requires them.
- Preserve correctness boundaries regardless of how small the design is: idempotency, exact ownership, accepted-send non-replay, operator intent, dependency integrity, atomic mutation, bounded retries, and evidence-based verification are mandatory. For concurrent read/modify/write flows, locking only the final database transaction does not prevent lost updates from stale snapshots: acquire one shared application owner before the authoritative read and hold it through persistence, keep slow external I/O outside the critical section, and do not treat a host-local lock as multi-host coordination.
- Add abstractions only for demonstrated repetition, a concrete invariant, or an independently replaceable boundary. Do not implement speculative future modes, plugin systems, compatibility layers, or generalized frameworks before they are needed.
- Remove retired or conflicting paths after the replacement is proven. Keeping two implementations of the same behavior increases ambiguity, CPU and I/O cost, testing burden, and recovery risk.
- Keep prompts and persisted context compact. Send stable system rules once per conversation generation; send only the current trigger context for each job. Do not repeatedly serialize state the worker already owns. For ephemeral session modes, make freshness a job-boundary rule: start a new session for each new job, keep the same live session across continuations of that job, and fail closed rather than silently replacing a lost ephemeral session mid-job.
- Treat names as configuration and behavior as reusable machinery. Maintainers is an agent identity, not a special architecture; another agent may use the same trigger only if it owns that trigger under the same shared rules.
- Prefer evidence-backed learning over automatic accumulation. Add or revise reusable lessons only when they are general, actionable, and likely to prevent recurrence; do not turn shared learning into a chronological incident log.

- Planning is implementation design, not a catalog of possible architecture. Before proposing new code, inventory the existing call path, helpers, classes, native platform features, and installed dependencies that already cover the requirement; choose the smallest root-cause change, name the exact files/tests that need to move, state what must not be built, and define a concrete stop condition. Do not widen a plan merely to make it look comprehensive.
- Reuse before extraction. Do not create a helper, wrapper, adapter, function, or class merely because a block can be named; keep direct code when it is clearer, reuse an existing primitive when one already fits, and extract only when demonstrated repetition, shared state, a shared invariant, or an independently testable responsibility makes the code simpler overall.
- When several operations genuinely share the same state, lifecycle, invariant, or responsibility, consolidate them into the existing cohesive class or one small cohesive class rather than scattering near-duplicate functions. Similar syntax alone is not a reason for a class, and one implementation does not justify an interface, factory, registry, plugin system, or generalized framework.
- Evaluate design by total effectiveness: correctness, operating cost, latency, failure surface, debuggability, and ease of change. Fewer lines or abstractions are not automatically better; the best solution is the smallest one that remains complete and robust.
- Destructive retention or cleanup must classify filesystem entries without following symlinks: reject symlinks before regular-file checks, constrain deletion to one exact owned namespace, and leave lookalikes or unowned recovery artifacts untouched.
- Treat cleanup or retention after an authoritative commit as maintenance rather than retroactive transaction success criteria. If the authoritative write is already durable, maintenance failure should preserve that success and surface a warning unless maintenance itself was the requested operation.
